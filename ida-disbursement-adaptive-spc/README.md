# Project 02 — Adaptive SPC on IDA disbursements

Project 01 ([ida-disbursement-spc](../ida-disbursement-spc)) learned its control limits once, from FY2010–2019, and applied them to every year after. This project asks what happens when the limits are **re-learned every year from a rolling window** — and measures it against the fixed baseline on the same data, with the same planted errors, under the same statistics.

Short answer, in advance: rolling limits catch more and monitor more countries, at the price of more collateral alerts and some brand-new blind spots. Several of those blind spots were only visible because this project built a chronological engine and a feed-failure test first. The details are below, with numbers.

**Data:** the same 374 KB country × fiscal-year extract as Project 01 (`data/` at the repository root). IDA only, gross disbursement only.

## Run it (PowerShell)

From the repository root:

```powershell
pip install -r ida-disbursement-adaptive-spc/requirements.txt
cd ida-disbursement-adaptive-spc

python src/a1_prepare.py                     # bronze -> silver with Project 01's rule layer (R1-R6)
python src/a2_adaptive_spc.py                # all four methods on the real data
python src/a3_evaluate.py                    # tuning draws  -> experiments/ledger.csv  (~3 min)
python src/a3_evaluate.py --split holdout    # hold-out draws, once per finished version (~3 min)
python src/a4_report.py                      # figures + outputs/COMPARISON.md

python -m unittest discover -s tests -v      # 18 regression tests
```

Windows PowerShell 5.1 has no `&&`; run the lines one by one, or chain with `;`. Python 3.11+, pandas, numpy, matplotlib — the same three dependencies as Project 01. The tests use the standard library's `unittest`, so nothing else needs installing.

Project 02 needs Project 01's **source** folder next to it (it imports from it), but not Project 01's outputs: it builds its own silver file and writes only inside `ida-disbursement-adaptive-spc/`.

## How it reuses Project 01

Nothing was copied. One module, [src/v1_bridge.py](src/v1_bridge.py), puts Project 01's `src/` on the import path and re-exports what is reused:

| reused unchanged from Project 01 | where it is used here |
|---|---|
| `config` — sigma multiplier, MAD scale, min baseline years, run length, severity threshold, windows, seeds, the five error types | every step; only *new* knobs live in [adaptive_config.py](src/adaptive_config.py) |
| `load_bronze`, `run_rules` (R1–R6), `add_period_completeness`, `coverage_report` | `a1_prepare.py` |
| `fit_chart`, `robust_z`, `explain`, `group_incidents` | the v2 engine in [adaptive_core.py](src/adaptive_core.py) |
| `stale_repeat_mask` (R6) | system recall in `a3_evaluate.py`, as in Project 01 |
| `build` + `add_growth` (the v1.1 chart itself) | the `v1.1-reference` method |
| `inject` (the five error injectors) | `a3_evaluate.py` — same seeds, same placements |

What had to be **adapted** rather than reused is the chart loop. Project 01's `build()` fits one chart per country and applies it to all years, which is only correct for a frozen baseline. The v2 engine re-orders the work so that every monitored year gets its own chart, built before that year is looked at.

**Proof the reuse is faithful:** the `v1.1-reference` row in this project's ledger is produced by Project 01's code on this project's silver file, and `a3_evaluate.py` checks at the end of every run that its recall numbers equal Project 01's published ledger to the decimal. Project 01's own pipeline was re-run after this project was built and regenerated byte-identical outputs.

## Four methods, compared on identical data

| method | baseline | recalibration | lifecycle | purpose |
|---|---|---|---|---|
| `v1.1-reference` | fixed FY2010–19 | — | no | Project 01, unchanged |
| `v2-fixed` | fixed FY2010–19 | confirm | yes | isolates the engine fixes |
| **`v2-rolling`** | **rolling 10 years** | **confirm** | **yes** | **the method this project proposes** |
| `v2-rolling-naive` | rolling 10 years | include all | no | ablation: textbook rolling limits |

`v2-rolling` vs `v2-fixed` isolates the effect of the rolling window. `v2-fixed` vs `v1.1-reference` isolates the engine fixes. `v2-rolling-naive` shows what the lifecycle handling and recalibration policy are protecting against.

## The method

### 1. Rolling baseline, and why it cannot see the future

For every monitored year *t*, in order, the engine:

1. chooses the baseline — the **most recent 10 eligible years before *t***;
2. computes year-over-year log growth `ln((x_y + c)/(x_{y-1} + c))` for those years, with `c` = 5% of the median level **of those baseline years** (floor $100k) — Project 01's stabiliser, but computed from the baseline only;
3. fits the chart with Project 01's `fit_chart` (median, 1.4826 × MAD, ±3σ, minimum 8 years) — which may refuse;
4. only then evaluates year *t*;
5. records *t*'s verdict, which the baseline of *t + 1* may need.

With no exclusions, "10 eligible years" is exactly the calendar window: FY2021 is judged on FY2011–2020, FY2026 on FY2016–2025. (FY2020 has 9 — FY2010 has no prior year to grow from.) When years are skipped, the look-back extends **further into the past**, never past *t*. → [adaptive_core.py `select_baseline`](src/adaptive_core.py)

Three regression tests enforce the no-leakage property directly: multiplying every value from FY2023 on by 7 must leave every FY2020–2022 verdict bit-for-bit identical; tripling the evaluated year must not move its own limits; and every baseline must end before its year.

### 2. Two defects in v1.1 this engine removes

**The sustained-shift rule looked ahead.** Project 01's `run_rule_flags` scans the whole series and, when 8 same-side points complete, flags **all 8 retroactively**. Azerbaijan's FY2020 "sustained shift" existed only because FY2021–2026 later continued the run; at FY2020 itself the run was 2 points long. A test reproduces this with Project 01's own function. The v2 rule flags *t* only if the run **ends at *t*** and consists of *t* and the 7 years before it.

**Growth bridged missing years.** Project 01 divides each row by the previous *row*. For a series with FY2022 missing, that makes FY2023 ÷ FY2021 — a two-year change charted as one. v2 computes growth only between adjacent fiscal years; the year after a gap is reported as `no_prior_year` and the pair never enters a baseline. Six IDA series have gaps (Syria, Sudan, Central Asia, Marshall Islands, Mauritius, Zimbabwe).

### 3. Zero periods — a minimal lifecycle, not a state machine

"Zero" means gross disbursement ≤ 0 **for lifecycle purposes only**: Azerbaijan's FY2019 −$16,372 refund counts as zero here, while the silver data and rule R2 keep the original value.

| year pattern | what the chart does | what is reported |
|---|---|---|
| positive → **zero** (onset) | evaluated normally | the drop, if it breaks the limits — the first unexpected zero is **still caught** |
| zero → **zero** (dormant) | **not evaluated** — $0 → $0 = 0% growth means nothing | nothing per year |
| a zero period of **2+ years** after earlier activity | — | **one lifecycle incident**, visible for as long as it lasts |
| zero → **positive** (reactivation) | evaluated normally | the jump, if it breaks the limits |
| any year whose growth touches a zero | — | **skipped from later baselines** — lifecycle, not ordinary variation |

The skipping rule is what handles reactivation without an 8-year wait: after a zero period, the baseline reaches back past it to the country's last active years. Afghanistan (zero in FY2023, positive again in FY2024) is charted again in **FY2025**.

Each lifecycle incident says whether repayments and commitments **also** dropped to zero. If they did, the whole country may have vanished from the feed, and the incident is raised to `medium`. If they continue (as for every real zero period in this data), it stays `info` and reads as a wind-down. Either way it is worded as an **observation about the data, not an IDA status** — a zero period does not prove a country left IDA.

R6 (stale repeat) needs no change: it only fires on positive values, so consecutive zero years never trigger it. A test locks that in.

### 4. Recalibration policy — what a flagged point does to later baselines

Excluding every flagged point forever would freeze a country's limits the first time its process genuinely changes. Including everything lets errors widen the limits that should catch the next one. The policy (`confirm`) sits between:

| flagged point at year *y* | treatment in baselines after *y* |
|---|---|
| the next year jumps back the opposite way and is flagged too (spike and reversal) | **transient** — both years held out permanently |
| the next year does not reverse it | **confirmed new level** — readmitted from *y + 2* |
| *y* is the year just before *t* | **unconfirmed** — held out at *t* |
| sustained-shift points | never held out (they sit near the centre and are the evidence the limits need) |

Bangladesh shows it cleanly: FY2020 (−29%) is flagged, held out of the FY2021 baseline, and readmitted at FY2022 once FY2021 did not reverse it. Every alert whose baseline skipped years says so in its explanation sentence.

### 5. Severity

v1.1 labelled every sustained-shift alert `medium`, so Azerbaijan's points at z = −0.07 came out medium. Now a shift is `medium` only if the median |z| of the run is ≥ 1, otherwise `low`. Incident severity is the worst member's (v1.1 only knew high/medium). Beyond-limits severity is unchanged: high at |z| ≥ 5.

## Evaluation

Project 01's harness, extended rather than rewritten ([a3_evaluate.py](src/a3_evaluate.py)):

- The five original error types use **Project 01's `inject` with the same per-type seeds**, so placements are identical. In every trial, **all four methods are scored on the same broken dataset** — the method is the only thing that differs.
- **New: `feed_stops`** — a country's gross set to zero from a random monitored year through FY2026. It is appended last in the catalogue so it cannot disturb the other five types' draws.
- Recall is on the **system** (chart + R6), as in Project 01, reported two ways: `recall` over the injections the method actually charts (Project 01's definition), and **end-to-end** over *all* injections, where an error in an unmonitored country counts as missed. Coverage differences only show up in the second.
- For `feed_stops` lasting 2+ years, two extra numbers answer *"did the baseline learn the failure as normal?"*: how often the chart evaluated the final year and called it **in control**, and how often anything still **surfaced** that country in the final year.
- Tuning draws (seed 7) for development; hold-out draws (seed 2026) run once per finished version. Every ledger row records the git commit (with `-dirty` if uncommitted), a hash of the files that define the method, and the parameters.

Development was done on the tuning draws; these are the numbers to quote. The tuning/hold-out gap on an unchanged method is up to ~5 points, so smaller differences between methods are not evidence.

### What the numbers say

**`v2-rolling` is the recommended method**, and the gain decomposes cleanly:

- **The engine fixes and lifecycle handling (v1.1 → v2-fixed)** remove the look-ahead in the sustained-shift rule — v1.1's 7 shift alerts could never have fired in a live monthly pipeline — and turn a dead feed from *"in control"* 75% of the time into *surfaced* 95% of the time. On their own, with a fixed baseline, they cost coverage (82 → 74 countries: one-off zero years in 2010–19 leave too few baseline years).
- **The rolling window (v2-fixed → v2-rolling)** wins that coverage back and more (74 → 84 countries), and raises drop-to-zero recall from 89.8% to **94.8%** (+5 on hold-out, +3 on tuning — consistent in direction). End-to-end recall improves on every error type.
- **The naive rolling chart is disqualified** despite the highest end-to-end recall: it calls a failed feed *in control* **86%** of the time. It covers more countries only because it charts dormant $0 → $0 years, and a rolling baseline full of zeros learns the failure. This is the case the recalibration policy and lifecycle handling exist for.

**Spike and misstatement recall do not change meaningfully** — the differences are inside the tuning/hold-out noise. The 25% misstatement stays undetectable (~12%) for every method: it is inside ordinary year-to-year variation, which no univariate 3σ chart can fix.

### Where the rolling baseline hurts

- **More collateral** — about 2–3 extra alerts per trial (+12–15%): tighter recent limits flag the rebound year after an error more often.
- **Recent calm tightens the limits** (14 of the 34 real-data alerts that differ from v2-fixed): Bosnia, Georgia, Ghana. Whether those are useful is a precision question the labels will answer.
- **Oscillating regimes do not get learned.** Kosovo swings +654%, −67%, +182%, −69%. Each pair looks like a spike and reversal, so the `confirm` policy holds every one out; the old volatile years roll out of the window and nothing replaces them. Kosovo's limits get **narrower** while it gets more volatile, and it contributes 3 of the 5 extra high-severity alerts. The fixed baseline has the mirror problem (it never adapts at all); a production fix would cap how many consecutive transients can be held out.
- **Feed-stop blind spots (5% of long stops):** a stop that erases *every* positive year a series has ever had looks identical to a country that was never active (22 real ones), so no lifecycle incident is raised; and a missing fiscal year inside a stop splits it into periods too short to report.

### What is still unknown

**Precision.** None of the alerts are labelled yet (Project 01's `labels/alert_labels.csv` is empty), so there is no evidence yet on whether rolling's *different* alerts are better or worse alerts — only that it catches more planted errors and costs more collateral. Labels are keyed on (country, fiscal year), so labelling the union of both methods' alerts once gives precision for both.

## Configuration

Everything new is in [src/adaptive_config.py](src/adaptive_config.py); everything shared is read from Project 01's `config.py`.

| setting | default | meaning |
|---|---|---|
| `WINDOW_YEARS` | 10 | eligible growth years in each rolling baseline |
| `LIFECYCLE_MIN_ZERO_YEARS` | 2 | zero periods this long become lifecycle incidents |
| `METHODS` | four entries | baseline type, recalibration policy, lifecycle on/off per method |
| `SHIFT_MEDIUM_Z` | 1.0 | median run |z| at which a sustained shift becomes medium |
| `C_FRACTION`, `C_FLOOR` | 0.05, $100k | growth stabiliser — same values as Project 01 |
| `METHOD_VERSION` | `p02-v1` | ledger key; bump whenever the engine changes |
| inherited | 3σ, MAD×1.4826, min 8 years, run 8, high at |z| ≥ 5, FY2020–26, seeds 7 / 2026, 40 per trial × 10 trials | Project 01 `config.py` |
